## 0. 確定した環境事実(T0調査より。以後の全判断の前提)

- **公開トップはWordPressではなく静的HTML**(`consult/index.html`)。GitHub `main` → Azure Static Web Apps で公開。WordPress側フロントページ(ID 18、slug `home`)は未使用
- **`main` へのpushは両Azure Static Web Apps(静的トップ・reserve系)をデプロイする**。したがって `main` へのpushは毎回、差分提示→承認が必須
- WordPress: 親テーマ Emanon Premium 1.7.5/WP 7.0.2/PHP 7.4.33/パーマリンク `/%postname%/`/プラグイン26件有効(W3 Total Cache・Really Simple Security・Site Kit・BackWPup・Code Snippets等)
- 子テーマ `kiduki-child`: ローカル作成済み・**本番未有効化**(T0-R1で対応)
- **旧メール送信資産は流用不能**: 送信はACS Email・Azure既定ドメイン(`.azurecomm.net`)であり、リソースグループごと2026年5月10日に削除済み。接続文字列・過去リード(Cosmos DB)・送信履歴は復元不能 → 送信基盤はXServerで新設(T2A)
- **現行問い合わせ導線の故障内容**: 静的トップ→ `reserve.kdkconslt-sngyouijm.com`(HTTP 200)→送信先の旧Azure FunctionはDNS解決不能。**API失敗時もブラウザのlocalStorageに保存して成功表示するため、利用者には完了に見えてリードはどこにも届いていない**。WordPress `/question/` はフォームなしで旧Azure相談ページへリンク。直通メールのフォールバックも無し
- フルバックアップ取得・SHA-256検証済み(DB 26.5MB/ファイル1.12GB、権限0600、Git管理外)
- BackWPup警告: 過去の復元作業の残存ファイルに**平文DB認証情報**が含まれる可能性(T0-R2で対応)

## T2A: 送信基盤の新設(XServer公式MCP/API)

旧送信資産は流用不能(§0)のため、XServerの公式API/MCP基盤で新設する。

**前提確認(最初に実行・報告)**
- `dig NS / dig MX / dig TXT` で `kdkconslt-sngyouijm.com` のネームサーバー・MX・SPFの現状を報告
- Azure Static Web Apps(静的トップ・reserve)のカスタムドメインを成立させているDNSレコードを一覧化する(**以後のDNS変更で絶対に壊さないため**)
- 本サーバーがXServer API/MCP Serverの対応環境であることを確認
- APIの機能一覧を確認し、今回必要な操作(メールアカウント作成/DNSレコード編集/DKIM設定/SPF確認)がAPIで実行可能かを○×で報告。**×の項目のみ**、院長向けの最小ランブック(実画面のラベル・貼り付け値・所要時間つき)に切り出す

**セットアップ**
- 院長作業(Phase 1で唯一・1回のみ): XServerアカウント「APIキー管理」でAPIキーを発行 → `.env`(gitignore済み)で受け渡し。**先に発行手順を1枚で提示すること**
- Codex: XServer MCP Server(またはCLI/API直接)を設定。APIキー・サーバー名は `.env`/MCP設定のみに置き、コミット・画面表示・ログ出力を禁止

**実行(各ステップ「計画提示→承認→実行→結果報告」を厳守)**
1. メールアカウント `info@kdkconslt-sngyouijm.com` を作成(強力なパスワードを生成して `.env` に保存。表示しない)
2. SPFの現状確認/DKIM有効化/DMARC(`p=none` から)のTXT追加。DNS変更は毎回、変更前後の差分一覧を提示してから適用。Azure SWA関連レコードには一切触れない
3. テストメール送信: Gmail・Outlook両方で**受信トレイ**着地を確認し、受信ヘッダの spf=pass/dkim=pass/dmarc=pass を確認して報告(迷惑メール着地なら原因特定まで次へ進まない)

**制約**
- API操作の対象は `kdkconslt-sngyouijm.com` と当該サーバーアカウントに限定。他ドメイン・他サイト・契約/支払い情報の操作は禁止
- Phase 1完了後、APIキーの失効・ローテーション方法を報告し、継続保有の要否は院長が判断する

## T2B: `/contact/` の構築(本書の最重要タスク)

**設計思想 — 三重の安全網**
1. **取りこぼさない**: 送信内容は必ずDBに保存(メールが落ちてもリードは残る)
2. **確実に届く**: PHP標準のmail()は使わず、SMTP認証+SPF/DKIM/DMARC(T2Aで構築済み)で送る
3. **壊れたら気づく**: 週次テスト送信の運用+フォーム外の連絡手段(メール)を常設

**事前確認**
- `/contact/` がWordPressに到達することを確認する(WordPressルート→静的トップへの301等、現行ルーティングの影響を受けないこと)
- W3 Total Cache のキャッシュ対象から `/contact/` と `/contact/thanks/` を除外する

**実装手順**
1. プラグイン導入(この4つ。これ以外は提案止まり): Contact Form 7/Flamingo(受信メッセージDB保存)/WP Mail SMTP/**CF7対応のハニーポット系スパム対策1つ**(選定理由を添えて提案→承認)
   ※Turnstile・reCAPTCHAは導入しない(外部アカウント不要のハニーポットで開始し、運用でスパムが観測されたら対策強化を提案する)
2. WP Mail SMTP: `sv***.xserver.jp`/ポート465/SSL/認証=メールアドレス全文(`info@kdkconslt-sngyouijm.com`)/パスワードは `.env` から
3. フォーム作成(`/contact/` 固定ページ。フォーム定義は付録A、メール文面・サンクス文言・フォールバック文言は `docs/copy/form-emails.md` の確定稿を一字一句使用)
   - 通知メールは**2宛先**(メイン+院長の携帯で受けられる予備)、送信元 `info@` 固定、**Reply-To=[your-email]**
   - 自動返信の送信元は受信監視している `info@`(**no-reply系は使用禁止**)
4. サンクスページ `/contact/thanks/` を作成(noindex)。子テーマ `assets/js/cf7-redirect.js` で送信成功時に遷移:
```js
document.addEventListener('wpcf7mailsent', function () {
  location.href = '/contact/thanks/';
}, false);
```
(functions.php で問い合わせページのみ読込)
5. 計測: Site Kit導入済みのため、GA4の設定状態を確認し、`/contact/thanks/` 到達をキーイベント(コンバージョン)として登録。GA4未接続なら接続から実施
6. フォールバック常設: フォーム下に「フォームが送信できない場合は、お手数ですが info@kdkconslt-sngyouijm.com まで直接メールでご連絡ください」
7. 運用ルールをREADMEに追記: 毎週月曜にテスト送信1件→DB保存・通知2通・自動返信の3点確認/月1回、Flamingo件数と受信メール件数を突合

## T4: 旧導線の301と差し替え

1. `reserve.kdkconslt-sngyouijm.com` **全パス** → `https://kdkconslt-sngyouijm.com/contact/` へ301。リポジトリ内の該当Azure SWAアプリを特定し、その `staticwebapp.config.json` の `routes` で設定する(DNS側での対応が必要な場合は差分提示→承認)
```json
{
  "trailingSlash": "auto",
  "routes": [
    { "route": "/*", "redirect": "https://kdkconslt-sngyouijm.com/contact/", "statusCode": 301 }
  ]
}
```
2. 旧相談ページ(静的側)→ `/contact/` へ301
3. WordPress `/question/` : 本文のリンクを `/contact/` へ修正するか、ページ自体を `/contact/` へリダイレクトするかを提案→承認→実装
4. 静的トップの問い合わせ・予約CTAを `/contact/` へ差し替え(T1のpushに同梱可。差分提示)
5. S1の暫定案内は301設定と同時に役目を終える(上書きされることを確認)
6. `main` push承認必須。push後、旧URL群からの301着地をPC・スマホで確認して報告
