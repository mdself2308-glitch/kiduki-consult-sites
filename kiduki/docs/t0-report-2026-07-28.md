## T0-1 本番構成とWordPressの棚卸し

- 公開トップはWordPressではなく `consult/index.html`。GitHubの `main` からAzure Static Web Appsへデプロイされる
- `https://kdkconslt-sngyouijm.com/` は静的トップへリダイレクトされる
- WordPressの管理/APIオリジンは `https://kdkconslt-sngyouijm.com`
- WordPress側フロントページ（ID 18、slug `home`）は公開トップとして使われていない
- WordPress 7.0.2、PHP 7.4.33、Emanon Premium 1.7.5、パーマリンク `/%postname%/`
- 調査時点で有効プラグインは26件。WordPressコア、親テーマ、プラグイン本体は直接編集しない
- `main` へのpushは2つのAzure Static Web Appsワークフローを起動するため、毎回、差分提示と明示承認を要する

## T0-2 旧Azure問い合わせフォームのメール送信資産

- 送信サービスは **Azure Communication Services Email（ACS Email）**。SendGridおよびMicrosoft 365ではない
- 送信元は独自ドメインではなく、**Azure既定ドメイン（`.azurecomm.net`）**
- 認証情報はクライアントHTMLや本リポジトリではなく、旧Azure Functionのサーバー側アプリ設定に置く接続文字列方式だった
- 旧Function、ACS Email、Cosmos DBを含むリソースグループは2026-05-10に削除済み。接続文字列/APIキー等の現物は現在存在せず、復元不能
- Git管理下に利用可能なAPIキー、接続文字列、パスワードはない。今後の秘密情報は `.env` または実行時の認証ストアだけで扱う
- 現在取得できる過去送信データ・送信履歴・過去リードはない。リード保存先だったCosmos DBも削除済みで、削除前の実データ件数や内容は確認不能
- 結論: 旧送信資産は流用せず、T2AでXServer上に新しい送信基盤を作る

## T0-3 現行問い合わせ導線の確認

- 静的トップから `reserve.kdkconslt-sngyouijm.com` への入口はHTTP 200で表示される
- 送信先だった旧Azure FunctionのホストはDNS解決不能
- API送信失敗時にもブラウザの `localStorage` へ保存して成功表示するため、利用者には完了したように見えるが、リードはサーバーへ保存・通知されない
- WordPress `/question/` にフォームはなく、旧Azure相談ページへのリンクだけがある
- 直通メールのフォールバックはない
- 結論: 2026-05-10以降、問い合わせ取りこぼしが起き得る状態。v2の順序どおり導線の止血と再構築を最優先とする
